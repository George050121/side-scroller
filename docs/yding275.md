# Yanhao Ding — Project 1 Write-up

## Repo and Codebase Organization

The project is a TypeScript side-scroller built on p5.js. `index.html` loads p5 and p5.sound globally, then imports the compiled `build/Main.js` as an ES module and attaches p5's required hooks (`preload`, `setup`, `draw`, `keyPressed`, `windowResized`) onto `window`, since p5 in global mode expects those names on the global scope. Everything else in `src/` is organized around one top-down chain of ownership:

- **`Main.ts`** is the p5 entry point. `preload()` constructs the single `GameManager`. `setup()` creates the canvas. `draw()` runs every frame: if the window is focused it calls `game.update()` then always calls `game.draw()`, and it scales the canvas to fit the window while keeping the game's fixed 800×600 logical resolution.
- **`GameManager.ts`** is a small state machine (`Loading → Menu → Running`, plus an unused `Finished`) built on plain `switch` statements over an internal `STATE` enum. In `Loading`, it waits for `ResourceManager.isLoaded()`, then builds the first `GameMap`, registers the arrow keys and space bar as `GameAction`s via `InputManager`, and drops into `Menu`. In `Running`, `update()` delegates physics to `map.update()`, polls the keyboard via `inputManager.checkInput()`, then translates the resulting `GameAction` states into player velocity/jump calls in `processActions()`. `draw()` just delegates to `map.draw()` (plus the settings overlay when in `Menu`).
- **`InputManager` / `GameAction.ts`** decouple "what key is down" from "what the game does about it." `InputManager` maps a p5 keyCode to a `GameAction` and, once per frame, asks p5's `keyIsDown()` whether that key is held and calls `press()`/`release()` on the action. `GameAction` is a tiny 4-state machine (`RELEASED → BEGIN_PRESS → PRESSED → END_PRESS → RELEASED`) so the game can distinguish "just pressed this frame" from "held" without every consumer re-deriving that from raw key events.
- **`ResourceManager.ts`** is the asset pipeline. It reads `assets/assets.json` (paths to images, spritesheets, sounds, and the `resources.json` sprite/map definitions), loads everything asynchronously through p5's loaders, then walks `resources.json` to pre-build one prototype `Sprite` per entry (`buildSprite`, keyed by a `type` string like `"Player"`, `"Grub"`, `"Star"`) with its animations already wired up. `GameMap.initialize()` later `.clone()`s these prototypes per tile/character in a level file.
- **`GameMap.ts`** is where a level actually lives: it parses a level's text map (`assets/maps/map*.txt`) into a `tiles[x][y]` grid plus a flat `sprites[]` array and a `player`, and it owns per-frame physics (`updateSprite`: gravity, horizontal-then-vertical tile collision via `getTileCollision`, then `checkPlayerCollision` against nearby sprites), win/lose logic (`Heart` advances the level, player `DEAD` resets it), the score (added by my teammate's feature), and camera-relative drawing (`draw()`, including the parallax math in `computeParallaxX` — the function I fixed for T4).
- **`src/sprites/`** is a small inheritance chain: `Sprite` (position/velocity/animation frames) → `Creature` (adds a `state` machine: `NORMAL/DYING/DEAD`, used by both enemies and the player) → `Player` (adds movement constants, jump, and — from my T5 feature — an invincibility countdown) and `Grub`/`Fly` (enemy speeds/flight). `PowerUp` and its subclasses (`Star`, `Music`, `Heart`, and my `Invincibility`) are plain `Sprite`s whose type is only used to decide what `GameMap.acquirePowerUp()` does on pickup.
- **`Settings.ts`** owns the pause/settings modal (`m` key) and the checkboxes for music/sound/fullscreen; it's also where T9's player-facing instructions are supposed to live.

**Data flow during one frame (Running state):** p5 calls `draw()` → `GameManager.update()` → `GameMap.update()` moves the player and every sprite by `velocity * deltaTime`, resolves tile collisions axis-by-axis, and checks player-vs-sprite collisions after each axis (this is why a stomp and a side hit are distinguished by an explicit `canKill` flag rather than by re-deriving direction from the collision box) → back in `GameManager`, `inputManager.checkInput()` reads the real keyboard state into the `GameAction`s → `processActions()` turns those into `player.setVelocity(...)`/`player.jump(...)` calls that will be picked up on *next* frame's physics step. Then `GameManager.draw()` → `GameMap.draw()` computes the camera's horizontal offset from the player's position, draws each parallax layer at a fraction of that offset (`computeParallaxX`), draws visible tiles and sprites shifted by the same offset, and draws the score HUD in fixed screen space.

## AI Tools Used

I used **Claude Code** exclusively; every session is logged automatically under `ai_log/` (session-logging hook, verified in T0 — see `ai_log/2026-09-08_09-34-21_0522b015.md` for the first verification session). Representative sessions and what I actually did with them:

- **T4 diagnosis and fix** (`ai_log/2026-09-08_09-34-21_0522b015.md` and the follow-ups that day): I asked Claude to trace how `computeParallaxX` was used from `GameMap.draw()` and explain what the pre-existing `tests/GameMap.parallax.test.ts` expected. It correctly identified that the function ignored `mapWidth`/`bgWidth` entirely (`return Math.trunc(offsetX)`) and proposed the ratio-based fix; I had it also add the `mapWidth === myW` zero-division guard once the test suite and a real merge with a teammate's independently-written guard made the edge case obvious. It got this right on the first pass — the main value was speed of narrowing down *which* function was wrong in a codebase I hadn't touched before, not correctness I had to double-check line by line, since the pre-written failing tests provided an objective check either way.
- **T5 feature (invincibility power-up)**: I asked it to find an existing, already-wired-but-unused extension point rather than bolt on something new, and it found that the `^` map tile and `powerup1-4` images were already routed through `resources.json` to a bare `PowerUp` class that did nothing on pickup — a better integration point than I'd have found by reading `GameMap.ts` alone. Where it fell short: my first instinct (and its first draft) tested the new collision behavior only with unit tests; it took explicitly asking it to *run the actual game* (via a scripted headless-browser session driving real key presses) to catch that the feature only "looks" correct in isolated tests — it also caught and explained an initially confusing result (enemies dying that seemed too far from the player) that turned out to be real game-clock drift between my manual verification steps, not a bug.
- **Git/GitLab process work**: several sessions were about verifying merge-conflict resolutions, reviewing a teammate's MR, and diagnosing why a freshly-pushed branch's MR still showed old T4 commits in its Commits tab. That last one is a good example of a real limitation: it initially assumed a straightforward force-push would fix the stale history, but a background auto-logging commit landed *during* the operation (while I was confirming the force-push) and silently reintroduced the old history; it had to notice the discrepancy on its own re-check afterward, diagnose the race, and redo the rebase in one uninterrupted pass. It never blindly declared success — it re-verified with `git log`/`git diff --stat` after every step — but I had to be the one who insisted "check whether GitLab actually shows what you claim" rather than trusting a single tool-call result.

Overall assessment: strongest at fast, systematic codebase archaeology (grepping/reading across files to find the real root cause instead of the first plausible one) and at not stopping until a claim was checked against a real, running instance of something (tests *and* the actual game *and* the actual pushed branch). Weakest when an action had a side effect outside the immediate command (a background hook firing mid-operation) — that required me noticing something still looked wrong and asking it to re-verify rather than accept the first "done."

## Best Practices Learned

- **Land infrastructure fixes before feature work, and say so explicitly in the plan.** `instructions.md` calling out "land T4 first" wasn't just a suggestion — main was genuinely red until it merged, and every teammate's branch inherited that. Sequencing work against a shared, gated `main` is a real project skill, not busywork.
- **CI and required-approval gates interact with history-rewriting in non-obvious ways.** A squash-merge on one branch orphans that branch's original commits from `main`'s ancestry even though the *content* is identical, which then resurfaces as confusing, duplicate-looking history on any branch built on top of the pre-squash commits. And GitLab's "reset approval on new push" protection means *any* push — even a no-op ai_log commit — can silently invalidate a teammate's review, which taught me to batch pushes and warn reviewers before pushing to an already-approved MR.
- **A green test suite is necessary but not sufficient.** Unit tests caught real logic bugs quickly, but the invincibility feature only proved itself when actually played — a lesson in verifying claims against the real artifact (the running game, the real MR page) rather than trusting an intermediate proxy (tests, a diff, a single git command's stdout) for the actual outcome.
- **Force-pushing and other destructive git operations deserve an explicit pause**, even when they're clearly the right fix and even when working with an AI assistant — confirming *before* rewriting shared history caught a race condition I'd have otherwise pushed straight through.
- **Working in an unfamiliar codebase goes faster by tracing one concrete frame of execution end-to-end** (input → physics → collision → draw) than by reading files in isolation; that's the same structure I used above to explain the codebase, because it's genuinely how I built a mental model of it.
