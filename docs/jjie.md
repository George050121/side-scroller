# Jingxue Jie — Project 1 Write-up

## Repo and Codebase Organization

The game is a TypeScript side-scroller built on p5.js, compiled to `build/` and loaded by `index.html` in p5's "global mode" (p5 hooks like `preload`/`setup`/`draw`/`keyPressed` are attached to `window` from `Main.ts`, rather than instantiated as a `p5` object). Almost everything under `src/` fits into one chain of ownership rooted at a single `GameManager`:

- **`GameManager.ts`** is the top of the chain: a small state machine (`Loading → Menu → Running`, plus an unused `Finished`) driven by p5's `update()`/`draw()` calls every frame. It owns one `ResourceManager`, one `InputManager`, one `Settings`, one `SoundManager`, and (once loading finishes) one `GameMap`. While `Loading`, it just polls `resources.isLoaded()`; once assets are ready it builds the first `GameMap` and registers the arrow keys/space bar as `GameAction`s. While `Running`, `update()` delegates physics to `map.update()`, reads the keyboard via `inputManager.checkInput()`, then in `processActions()` translates the resulting press-states into `player.setVelocity(...)`/`player.jump(...)` calls.
- **`InputManager` / `GameAction.ts`** are a generic, game-agnostic input layer. `InputManager` maps a p5 keyCode to a `GameAction` and asks p5's `keyIsDown()` once per frame whether that key is held. `GameAction` is a tiny 4-state machine (`RELEASED → BEGIN_PRESS → PRESSED → END_PRESS → RELEASED`) so downstream code can ask "was this just pressed this frame?" instead of re-deriving that from raw key events every time. Neither file knows anything about the player or the map — `GameManager.processActions()` is the only place that connects "space is pressed" to "the player should jump."
- **`ResourceManager.ts`** is the asset pipeline. It reads `assets/assets.json` for the list of images/spritesheets/sounds/text files and a `resources.json` describing sprite definitions and map/level lists, loads everything asynchronously through p5's loaders (`loadImage`, `loadSound`, `loadJSON`, `loadStrings`), and then walks `resources.json` to pre-build one prototype `Sprite` per entry via `buildSprite` (keyed by a `type` string like `"Player"`, `"Grub"`, `"Star"`, `"Invincibility"`), with animation frames already attached. `GameMap` later `.clone()`s these prototypes for each tile character it sees in a level file.
- **`GameMap.ts`** is where a level actually lives and runs. `initialize()` parses a level's text map (`assets/maps/map*.txt`) into a `tiles[x][y]` grid, a flat `sprites[]` array, and a `player`. `update()` drives per-frame physics (`updateSprite`: apply gravity, move on the x-axis, resolve tile collision, move on the y-axis, resolve tile collision again, check player-vs-sprite collision after each axis) and game rules (a `Heart` pickup advances the level; the player reaching `DEAD` resets the level and the score). `draw()` computes a camera offset from the player's position and draws parallax background layers, tiles, sprites, and the player, all shifted by that offset, plus the score HUD. The parallax math lives in the standalone `computeParallaxX` function at the top of the file.
- **`src/sprites/`** is a short inheritance chain: `Sprite` (position, velocity, per-animation frame lists) → `Creature` (adds a `NORMAL/DYING/DEAD` state machine, shared by enemies and the player) → `Player` (movement constants, jump, and an invincibility countdown) and `Grub`/`Fly` (enemy speed/flight behavior). `PowerUp` and its subclasses (`Star`, `Music`, `Heart`, `Invincibility`) are plain sprites whose runtime type is only used by `GameMap.acquirePowerUp()` to decide what happens on pickup — score, level advance, or a timed player buff.
- **`Settings.ts`** owns the `m`-key pause/settings modal: the music/sound/fullscreen checkboxes, and — as of my T9 work — the "How to Play" instructions block shown at the top of that same modal.

**Data flow during one frame while `Running`:** p5 calls `draw()` → `GameManager.update()` → `GameMap.update()` moves the player and every other sprite by `velocity * deltaTime`, resolving tile collisions one axis at a time and checking player-vs-sprite collisions after each axis (this is why a stomp and a side/underneath hit are distinguished by an explicit `canKill` boolean passed into `checkPlayerCollision`, rather than re-derived from the collision geometry) → back in `GameManager`, `inputManager.checkInput()` reads the real keyboard into the registered `GameAction`s → `processActions()` turns those into velocity/jump calls that take effect on *next* frame's physics step, since this frame's movement already happened. Then `GameManager.draw()` → `GameMap.draw()` computes the camera's horizontal offset from the player's position, draws each parallax layer scaled by that offset through `computeParallaxX`, draws the visible tile window and sprites shifted by the same offset, and draws the score HUD in fixed screen coordinates on top.

## AI Tools Used

I used **Claude Code** exclusively; sessions are logged automatically to `ai_log/` (the hook itself needed a real fix mid-project — see below). Representative sessions:

- **Understanding the five core systems** (`ai_log/2026-09-15_09-21-02_984513ff.md`): I asked it to read `GameManager.ts`, `ResourceManager.ts`, `GameMap.ts`, `InputManager.ts`, and `GameAction.ts` together and explain how they connect. It traced one concrete frame end-to-end (input → physics → collision → draw) instead of describing each file in isolation, which is exactly how I built the mental model I wrote up above — I used the same "trace one frame" structure because it's genuinely how I now think about the codebase, not because it sounded good.
- **Verifying the T4 parallax fix was real, not just present** (`ai_log/2026-09-15_09-22-49_984513ff.md`): rather than just reading `computeParallaxX` and asserting it looked right, it ran `tests/GameMap.parallax.test.ts` directly (`npx vitest run`), confirmed all 4 cases passed, and separately ran `git diff HEAD -- src/GameMap.ts` to confirm the fix was actually committed to `main` and not sitting uncommitted. That distinction mattered — a fix that reads correctly but isn't merged doesn't help the team.
- **Auditing that both T5 features actually have tests** (`ai_log/2026-09-15_09-24-25_984513ff.md`): it didn't just list files under `tests/`; it cross-referenced commit authorship (`git show --no-patch --format='%an'`) against branch names to correctly figure out that the *merge* commit author and the *feature* commit author were different people (a teammate's merge can show up under either person's name in GitLab-style workflows), which is a real gotcha I wouldn't have caught by skimming `git log --oneline`.
- **Checking my T9 player-instructions-modal commit against the actual requirements** (`ai_log/2026-09-15_09-29-42_984513ff.md`): rather than taking the modal's own text at face value, it cross-checked every line I wrote ("M: Open or close this menu", "Escape: Toggle fullscreen") against the real key-handling code in `Main.ts` (`grep -n "keyPressed\|toggleMenu\|ESCAPE"`) to confirm the bindings I documented actually match what the game does. It also used `git log --follow -p -- src/Settings.ts` to notice that a teammate's later commit had appended a fifth line about the invincibility power-up to the same block I added — something I hadn't registered as a change to "my" commit, and worth knowing since the modal I'm claiming credit for isn't exactly what ships today.
- **Fixing the `ai_log` hook itself** (`ai_log/2026-09-15_09-16-22_d17b2575.md`): the debug output showed garbled characters, and it correctly diagnosed the root cause as `log_ai.py` opening files with the OS default codepage (GBK on this Windows machine) instead of UTF-8, rather than something wrong with the log content itself — a genuinely non-obvious bug since the garbling only showed up in the terminal's *display* of the debug output, not in the file on disk.

Where it fell short: while investigating T7 assets, one of its own exploration commands was a `for` loop that ran the same `git log --all --grep=""` four times and printed the identical full log each time — wasted output that added noise rather than signal, and something I had to notice rather than something it flagged. It's also worth being honest that its "codebase organization" and "AI tools" writing here is drafted *by* Claude Code from our actual conversation and command history, not typed by me first and merely checked — I read and edited it for accuracy, but I want to be upfront about that rather than imply otherwise.

Overall assessment: it was strongest at refusing to take a claim on faith — re-running tests, checking `git diff`/`git log` against what it had just asserted, and searching before answering "does X exist" instead of guessing. It was weakest at command hygiene during open-ended exploration (redundant commands, more `git log` invocations than the question needed), which is a minor efficiency cost but not a correctness one — every claim it gave me was still checked against real command output before I acted on it.

## Best Practices Learned

- **Never trust "the code looks right" — run it.** The parallax fix and the T5 feature tests all got verified by actually invoking `vitest`, not by reading the diff and pattern-matching against what correct looked like. A test suite that exists but was never re-run after a change isn't evidence of anything.
- **`main` being protected changes your daily workflow, not just your merge process.** The session-logging hook's auto-push failing on `main` was a direct, immediate consequence of forgetting to branch first (T0's own step 0 warns about this) — branch discipline isn't an abstract Git best practice here, it's the thing standing between me and a broken push.
- **`git log @{u}..HEAD` / `git diff @{u}..HEAD` are the right tools for "what have I committed but not shared yet,"** and checking that *before* trying to push (especially on a protected branch) avoids finding out the hard way. Creating a branch off the current commit and resetting the stale one back to match `origin` is the safe way to relocate unpushed work without losing it.
- **Authorship in a two-person repo is not always what the merge commit says.** A merge commit's author is whoever clicked merge, not necessarily who wrote the code; `git show --no-patch --format='%an'` on the actual feature commit (not the merge commit) is what actually answers "who did this."
- **An AI assistant that verifies its own claims is more useful than one that answers fast** — but that doesn't mean every command it runs is worth running. Reading its own tool output critically (not just its final prose summary) is part of using it well, which is why I flagged the redundant `git log` loop above instead of leaving it out.
